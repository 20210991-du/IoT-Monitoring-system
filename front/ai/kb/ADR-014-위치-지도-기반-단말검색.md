# ADR-014 · 위치/지도 기반 단말 검색 도구

## 맥락

[[ADR-013-챗봇-운영강화-도구확장-영구저장-캐시-audit]] 까지 12 도구 (기본 6 + 고급 6) 보유. 하지만 다음과 같은 자연어 질문 처리 불가:

- "은파 호수 공원 근처 장비"
- "군산시청에서 가장 가까운 단말 5대"
- "미룡동 단말 알려줘"
- "TB24-250401 주변 1km 안 단말"

기존 도구로는 단말 ID, 시설번호, 구역 정도만 검색 가능. **지명·랜드마크 자연어** 검색 안 됨.

DB 자원:
- `kscg_facility_info.POSITION` — 한국어 풍부 ("미룡동 834-13번지", "대야 버스터미널 앞", "군산시립박물관 앞")
- `kscg_facility_info.LATITUDE / LONGITUDE` — 정확한 좌표 (소수점 4~7자리)
- 군산 전체 55 단말 좌표 모두 있음

## 결정

**3 가지 위치 도구 도입** — DB 직접 매칭 + 외부 geocoder + 거리 계산.

### 1) search_devices_by_location(query, limit)

POSITION + facility number LIKE 매칭 (한국어 OK):
- 공백 다중 토큰 → AND
- 5 토큰까지
- 외부 API 의존성 X, 빠름 (~10ms)

사용 케이스:
- "미룡동" → POSITION '%미룡동%'
- "시청 앞" → POSITION '%시청%' AND POSITION '%앞%'
- "해망동 DM기술" → POSITION '%해망동%' AND POSITION '%DM기술%'

### 2) geocode_location(query)

OpenStreetMap **Nominatim** API 호출 (free, no key):
- 군산 우선 검색 (자동 "군산" 추가, viewbox 군산 영역)
- 한국어 accept-language=ko, countrycodes=kr
- User-Agent 헤더 필수 (Nominatim ToS)
- 8초 timeout
- 1초당 1 요청 (rate limit) — 우리 사용량 낮음

사용 케이스:
- "은파호수공원" → {lat: 35.97, lng: 126.69}
- "군산시청" → DB 에 "시청 민원실 입구" 있어도 명확한 좌표 필요할 때

### 3) find_devices_near(lat, lng, radiusKm, limit)

좌표 + 반경 검색, **Haversine 대권 거리** 계산:
- radiusKm 0.1~30 클램프, 기본 2.0
- 가까운 순 정렬, distanceKm 동봉

사용 케이스:
- 단말 lat/lng 받았으면 → 그 좌표 부근 검색
- geocode 결과 받아 자연어 위치 → 단말 매칭

### LLM 위치 질문 흐름 (시스템 프롬프트 명시)

1. **DB 텍스트 매칭 가능** → search_devices_by_location 단일 호출
2. **일반 지명** (DB POSITION 에 없을 때) → geocode_location → find_devices_near 2단계
3. **단말 ID 부근** → get_device_detail → find_devices_near

## 구현 (server.js +176 줄)

- TOOLS 배열에 3 개 추가 (12 → 15)
- haversineKm 헬퍼 (상단)
- execToolInternal switch 에 3 case 추가
- CACHEABLE_TOOLS 에 3 개 모두 추가 (LRU 10초)
- buildSystemPrompt 의 "도구 가이드" 카테고리에 "위치/지도 (3)" 신설

위치 10 + 기본 10 + 복합 10. 결과: **30/30 PASS** (5/18 검증).

## 발견된 잠재 이슈 (1건 fix)

**환각 이슈** — context={} 로 호출 시 시스템 프롬프트가 "전체 0대" false 정보 주입.
- 증상: B05 "전체 KPI" 질문 시 LLM 이 도구 호출 없이 "전체 0대" 답변
- 원인: `counts.all ?? 0` 로 빈 객체를 0대로 표시
- 수정: hasContext 가드 — 컨텍스트 없으면 "(get_summary 호출 필수)" 로 명시
- 효과: B05 가 SOFT → PASS 로 전환

## 성능

- search_devices_by_location: ~5 ms (POSITION LIKE, 55 row scan)
- geocode_location: ~300~800 ms (외부 API, 1초 timeout)
- find_devices_near: ~6 ms (Haversine + JS sort, 55 row)

## 트레이드오프

**장점:**
- 자연어 위치 질문 처리 가능 (지명, 랜드마크, 단말 부근)
- 외부 의존성은 geocode 만 (다른 둘은 DB 만)
- Nominatim 무료 + 한국 데이터 풍부

**단점:**
- Nominatim rate limit 1 req/sec (대량 호출 시 캐시 필수, 이미 캐시 적용)
- Nominatim 한국 데이터가 일부 부정확 (작은 마을·신축 시설)
- POSITION 자체에 오타·표기 차이 (예: "방송국" vs "MBC") — search 매칭 한계

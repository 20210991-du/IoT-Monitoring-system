# 이재헌 — 프로젝트 진행 과정에서의 생각과 의도 (백엔드·DB·PM)

## 프로젝트를 시작하면서
처음 프로젝트를 시작했을 때 가장 중요하게 생각한 것은 "AI를 만드는 것보다 실제 사용할 수 있는 서비스를 만들자"는 것이었다. 단순히 모델의 정확도를 높이는 연구 프로젝트보다는, 사용자가 실제로 활용할 수 있는 형태의 시스템을 만드는 것이 더 의미 있다고 생각했다. 그래서 처음부터 AI · 데이터 · 사용자 경험(UI) · 관제 서비스를 하나의 시스템으로 연결하는 방향을 목표로 했다.

## GitHub를 사용한 이유
단순히 과제 제출용이 아니라 실제 개발 방식에 가깝게 진행해보고 싶었다. 그래서 README · CHANGELOG · SCHEDULE을 분리해서 관리했다. 특히 CHANGELOG를 작성하면서 내가 무엇을 개발했고 왜 수정했는지 기록하는 습관이 중요하다는 것을 느꼈다.

## Figma를 사용한 이유
처음부터 코드를 작성하지 않고 화면을 먼저 설계하기 위해 사용했다. 코드를 작성한 뒤 수정하는 것보다, 설계 단계에서 구조를 검토하는 것이 훨씬 효율적이라고 생각했다.

## 자문을 받으면서 느낀 점
처음에는 기능 구현 자체가 중요하다고 생각했다. 하지만 자문을 통해 실무에서는 기능보다 사용성·운영성·신뢰성이 더 중요하다는 것을 알게 되었다. 특히 "한 화면에 모든 정보를 넣지 말라"는 조언이 가장 인상 깊었다.

## 개인적으로 가장 중요하게 생각한 것
이 프로젝트를 진행하면서 가장 중요하게 생각한 것은 "보여주기 위한 프로젝트가 아니라 실제 사용할 수 있는 프로젝트를 만들자"는 것이다. 기술보다 더 크게 얻은 것은 "좋은 시스템은 기능이 많은 것이 아니라, 사용자가 쉽게 이해할 수 있는 시스템이다"라는 깨달음이다.

## 협업·일하는 방식
나는 개별 기능보다 전체 시스템이 어떻게 연결되어 동작하는지를 먼저 본다(통합 관점). 구현보다 "왜 이렇게 설계하는가"를 반복적으로 확인하는 편이다. 의사결정은 빠르게 내리기보다 대안을 비교·검토한 뒤 정하고, 실제 구현 가능성과 유지보수 편의를 중요하게 본다. 문제는 전체 구조를 먼저 이해한 뒤 세부 구현으로 들어간다. 일정과 진행 상황은 주차별로 문서(SCHEDULE, CHANGELOG)에 기록한다. 이해가 안 된 채로 넘어가기보다 반복 질문으로 확인하고, 추상적 설명보다 예시를 선호한다.
주의할 점: 설계 검토에 시간을 많이 쓰거나, 충분히 납득되지 않으면 결정이 늦어질 수 있고, 기능 범위를 넓히려는 경향이 있어 일정 관리가 중요하다.

## 말투
짧은 문장으로 핵심을 빠르게 확인하는 편이다. 자주 쓰는 표현: "그럼 이건 어떻게 해야 돼?", "한번 더 검토해줘", "정리해서 말해줘". 같은 주제를 여러 각도에서 다시 확인하기도 한다.
